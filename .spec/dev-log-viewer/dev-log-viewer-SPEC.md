# 实时开发日志查看器 SPEC

## 1. 背景

Smart Recruit 已拆分为 8 个 Go 业务服务、1 个 Go Gateway 和 3 个 Vite 前端。当前本地开发主要通过仓库根目录的 `start-dev.sh` 启动，脚本将每个进程的标准输出和标准错误覆盖写入 `.dev/logs/<service>.log`，并将 PID 写入 `.dev/pids/<service>.pid`。

服务数量增加后，开发者需要在多个文件之间切换，难以持续观察实时输出、快速筛选异常、关联 `request_id`/`trace_id`，也难以在日志高峰或服务重启时判断当前查看状态。

本功能建设一个仅用于本地开发的实时日志查看网站。设计基线位于 `.spec/dev-log-viewer/design/`：

- `screens/`：界面和状态的视觉事实源；
- `DESIGN.md`：颜色、字体、间距和组件 Token；
- `html/`：Stitch 导出的布局结构参考；
- `IMPLEMENTATION_NOTES.md`：设计资料优先级和运行时事实。

当设计样例与仓库事实冲突时，以当前源码、`start-dev.sh`、`stop-dev.sh` 和本 SPEC 为准。

## 2. 目标

- G-001：在单个浏览器页面中查看 12 个本地服务的实时日志。
- G-002：支持按服务、日志级别和文本快速筛选，并能定位 `request_id`、`trace_id` 等关联字段。
- G-003：正确处理日志文件首次出现、追加、截断、删除重建和服务重启。
- G-004：在高日志量、浏览器暂停跟随、SSE 断线重连等情况下保持状态可解释、资源有上限。
- G-005：提供符合已确认设计稿的 React + TypeScript + Vite + Tailwind CSS 界面，兼顾 1440×900 和 1366×768 桌面/笔记本屏幕。
- G-006：保持工具本地只读，不改变现有业务服务、Gateway、日志库、数据库、Proto 或认证体系。
- G-007：提供单一 Go 进程承载 API、SSE 和构建后的静态前端，降低本地使用成本。

## 3. 非目标

- NG-001：不建设生产级集中日志平台，不替代 Loki、ELK、Vector 或云日志服务。
- NG-002：不长期存储、索引或归档日志，不提供跨开发会话历史检索。
- NG-003：不在第一版提供启动、停止、重启业务服务的 Web 操作。
- NG-004：不从浏览器直接访问本地文件系统。
- NG-005：不提供任意文件路径浏览、目录遍历或用户自定义日志源。
- NG-006：不修改 Go 服务、Gateway、Vite 的现有日志格式，也不强制改为 JSON。
- NG-007：不接入业务 Gateway，不新增业务权限、角色、数据库表、Proto 或消息队列。
- NG-008：不以移动端为主要目标；小于 768px 的布局只需保证基础可用，不要求完整多栏体验。
- NG-009：不直接复用 Stitch 导出的 CDN HTML 作为生产代码。

## 4. 用户可见行为

### 4.1 页面入口与总体布局

- UI-001：用户通过本机地址访问日志查看器，默认地址为 `http://127.0.0.1:8090`。
- UI-002：默认页面由顶部工具栏、服务侧栏、筛选栏、日志主区域和底部状态栏组成。
- UI-003：1440×900 及以上宽度展示完整服务侧栏；1366×768 等较小桌面宽度允许侧栏折叠，并保证日志区域是视觉主体。
- UI-004：详情面板默认关闭；选中日志后以可调整宽度的分栏方式打开，不得覆盖日志正文。
- UI-005：页面整体固定在视口内，仅服务列表、日志列表和详情面板各自按需要滚动，不出现页面级双滚动条。

### 4.2 服务目录和状态

- UI-006：服务侧栏展示“全部服务”，并按 Backend、Gateway、Frontend 分组。
- UI-007：服务目录必须使用以下仓库事实，不得使用设计稿中的虚构或缩写名称：

| 分组 | 服务 | 端口 | 日志文件 |
| --- | --- | ---: | --- |
| Backend | `identity-service` | 50061 | `.dev/logs/identity-service.log` |
| Backend | `recruitment-service` | 50062 | `.dev/logs/recruitment-service.log` |
| Backend | `interview-service` | 50063 | `.dev/logs/interview-service.log` |
| Backend | `offer-service` | 50064 | `.dev/logs/offer-service.log` |
| Backend | `notification-service` | 50065 | `.dev/logs/notification-service.log` |
| Backend | `ai-agent-service` | 50066 | `.dev/logs/ai-agent-service.log` |
| Backend | `analytics-service` | 50067 | `.dev/logs/analytics-service.log` |
| Backend | `worker-service` | 50068 | `.dev/logs/worker-service.log` |
| Gateway | `smart-recruit-gateway` | 8080 | `.dev/logs/smart-recruit-gateway.log` |

- UI-008：运行状态表示“PID 文件存在且对应本机进程存活”，不得误标为业务健康、readiness 或依赖健康。
- UI-009：服务项展示端口、运行状态和日志文件最后更新时间；日志文件不存在时仍展示服务项。
- UI-010：用户可以选择单个、多个或全部服务；服务选择影响日志展示和后续流订阅。

### 4.3 实时日志与详情

- UI-011：首次连接默认加载每个已选服务最后 300 行日志，然后持续追加新日志。
- UI-012：日志行至少展示观察时间/源时间、级别、服务、调用位置和消息；缺失字段显示为空或 `UNKNOWN`，不得伪造。
- UI-013：日志级别支持 `DEBUG`、`INFO`、`WARN`、`ERROR`、`FATAL` 和 `UNKNOWN`；筛选器至少支持全部、INFO、WARN、ERROR。
- UI-014：Go 控制台日志中的 ANSI 控制序列不得原样污染页面；级别色由 UI 语义样式渲染。
- UI-015：连续的 Go 堆栈或多行错误应作为同一日志记录的详情呈现；列表默认仅展示一行摘要。
- UI-016：点击日志行打开详情面板，显示完整消息、全部行、服务、级别、调用位置、时间以及可识别的结构化字段。
- UI-017：可识别字段至少包括 `request_id`、`trace_id`、`span_id`、`grpc_code`、`elapsed`；字段不存在时不显示占位值。
- UI-018：用户可以复制单条完整日志、`request_id` 或 `trace_id`；复制失败必须给出可见反馈。
- UI-019：点击 `request_id` 或 `trace_id` 可在当前客户端缓冲区内筛选同一关联值的日志，不发起业务系统查询。

### 4.4 搜索、筛选与跟随

- UI-020：搜索支持对当前客户端缓冲区进行不区分大小写的普通文本匹配。
- UI-021：日志级别和服务筛选可以与文本搜索组合，所有条件采用 AND 语义。
- UI-022：无匹配结果时保留当前查询和筛选条件，显示“无匹配日志”状态，并提供清除筛选操作。
- UI-023：默认启用自动跟随最新日志；用户向上滚动后停止自动跟随，但继续接收日志。
- UI-024：停止跟随后显示“跳转到最新日志”操作，并显示尚未查看的新日志数量。
- UI-025：显式“暂停”只冻结列表可见更新，不主动断开 SSE；恢复后显示仍在缓冲区内的新日志。
- UI-026：“清空视图”只清空浏览器当前缓冲区，不得截断、删除或改写 `.dev/logs` 文件。
- UI-027：“导出”将当前筛选结果按当前显示顺序生成纯文本 `.log` 文件；导出只使用浏览器当前缓冲区，不请求服务器读取额外历史，不支持 JSONL。
- UI-028：侧栏折叠状态和详情面板宽度使用模块专用 localStorage key 跨刷新保存；日志内容、搜索词、服务选择和级别筛选不得持久化。

### 4.5 连接、空状态与高流量状态

- UI-029：SSE 连接状态至少区分连接中、已连接、重连中和已断开。
- UI-030：断线后保留已接收日志，并展示非阻塞重连横幅；自动重连不得用模态框阻止查看历史缓冲区。
- UI-031：重连横幅展示重试状态，并允许用户手动触发重连。
- UI-032：全部服务未运行或所有日志文件均不存在时，显示“未检测到服务”，并提示运行 `./start-dev.sh`；服务侧栏仍展示 12 个离线服务。
- UI-033：服务器或客户端缓冲区发生丢弃时，页面展示累计丢弃数量、缓冲区压力和告警状态，不得静默丢弃。
- UI-034：日志文件被截断或替换时，页面插入该服务的“日志源已重置/服务可能已重启”分隔事件，然后继续跟随新内容。
- UI-035：页面必须持续展示本地日志可能包含个人数据或凭据的提示，并明确查看器不可暴露到局域网或公网。

## 5. 功能需求

### 5.1 服务目录

- FR-001：后端必须维护固定服务白名单，包含 UI-007 的 12 个服务、分组、端口、PID 文件和日志文件。
- FR-002：任何 HTTP 参数不得扩展白名单或直接转换为文件系统路径。
- FR-003：后端必须定期读取 PID 和日志文件元数据，并通过服务目录 API 返回状态。
- FR-004：PID 状态判定必须处理 PID 文件缺失、空内容、非数字、陈旧 PID 和无权限检查等情况。

### 5.2 文件跟随

- FR-005：后端必须读取现有文件末尾快照并持续读取追加内容，不得从头加载无上限历史。
- FR-006：每个服务的默认初始快照为最后 300 行；服务端必须将客户端可请求的最大 tail 行数限制为 1000 行/服务。
- FR-007：必须正确处理 UTF-8 分片、跨读取块的半行以及最后一行尚未换行的情况。
- FR-008：必须检测同一文件大小回退、文件身份变化、删除和重新创建，并恢复读取。
- FR-009：单个服务文件异常不得终止其他服务的跟随。
- FR-010：服务端应去除 ANSI 控制序列并保留原始文本语义；不得将日志内容解释为 HTML。
- FR-011：日志解析失败时仍应以 `UNKNOWN` 级别和原文本输出，不得丢弃整条记录。

### 5.3 SSE 流

- FR-012：浏览器与后端之间使用单条 SSE 连接承载当前订阅服务的日志事件。
- FR-013：SSE 响应必须使用 `text/event-stream`、禁用缓存，并定期发送心跳，避免空闲连接被误判断开。
- FR-014：每个事件必须包含单调递增事件 ID；客户端重连时使用 `Last-Event-ID` 尝试补发服务器内存环形缓冲区中的事件。
- FR-015：若 `Last-Event-ID` 已超出可恢复范围，服务端必须发送 reset/snapshot 信号并重新提供有界快照，不得假装无缝续传。
- FR-016：每个客户端使用有界发送队列；队列溢出时记录丢弃数量并发送 `dropped` 事件。
- FR-017：慢客户端不得阻塞文件读取器或其他客户端。
- FR-018：客户端断开后，服务端必须及时释放订阅和连接资源。

### 5.4 客户端状态

- FR-019：客户端日志缓冲区默认最多保留 10,000 条记录，超过上限时淘汰最旧记录并增加客户端丢弃计数。
- FR-020：客户端必须区分“暂停渲染”“停止自动跟随”和“SSE 断开”，三者状态不可混淆。
- FR-021：筛选和搜索只作用于客户端缓冲区，不改变或删除服务器端日志。
- FR-022：页面刷新后允许重新获取有界快照；第一版不要求持久化筛选条件或日志缓冲区。
- FR-023：客户端必须支持将当前筛选结果导出为 UTF-8 纯文本 `.log` 文件；导出大小受 10,000 条客户端缓冲上限约束，不新增服务端导出 API。
- FR-024：客户端只持久化侧栏折叠状态和详情面板宽度，并对 localStorage 内容做类型、范围和版本校验。

### 5.5 本地运行和静态资源

- FR-025：构建后的 React 静态资源由 Go 二进制内嵌并同源提供，正常使用只需启动一个查看器进程。
- FR-026：前端开发模式允许 Vite 代理本地 Go API，但生产式本地运行不得依赖 CDN。
- FR-027：必须提供模块 README，并通过 `start-dev.sh`/`stop-dev.sh` 增加显式 `logs|log-viewer` target；查看器不加入无参数或 `all` 默认集合。
- FR-028：查看器退出不得影响任何业务服务或前端进程。

## 6. 非功能需求

- NFR-001（时延）：文件完成换行写入后，在正常本地负载下 95% 的日志应在 500ms 内出现在已连接页面。
- NFR-002（资源）：空闲状态下不得持续高 CPU；文件轮询或通知机制必须有节流。
- NFR-003（有界性）：文件快照、服务器事件环、客户端队列和浏览器日志列表均必须有明确上限。
- NFR-004（隔离性）：单个损坏日志文件、单个慢客户端或单条超长日志不得导致整个查看器退出。
- NFR-005（可测试性）：服务目录、tail、截断/替换、ANSI 清理、解析、SSE 重连和客户端状态转换必须可通过自动化测试验证。
- NFR-006（可维护性）：Go 后端按 catalog/tailer/parser/stream/http 分责；React 前端按组件、hooks、状态模型和类型分责。
- NFR-007（可访问性）：交互元素可通过键盘访问，具有可见焦点；状态不可只依赖颜色表达。
- NFR-008（视觉）：实现遵循 `.spec/dev-log-viewer/design/DESIGN.md`；不得联网加载字体，日志行和界面文本分别使用 JetBrains Mono/Inter 的系统可用版本或兼容系统回退字体。
- NFR-009（响应式）：在 1440×900 与 1366×768 下不得遮挡日志主列或产生页面级水平溢出。
- NFR-010（兼容性）：支持仓库当前主要本地开发环境；Windows 原生不作保证，WSL2 视为 Linux 环境。

## 7. 兼容性要求

- CR-001：不得改变现有 `start-dev.sh` 的既有目标、端口、环境变量默认值和服务启动顺序。
- CR-002：不得改变现有 `stop-dev.sh` 对既有目标的停止行为。
- CR-003：不得改变 `.dev/logs/<service>.log` 和 `.dev/pids/<service>.pid` 的命名约定。
- CR-004：不得要求业务服务改用新的 logger、日志级别或 JSON 格式。
- CR-005：不得修改业务 Gateway 路由或将本地文件读取能力暴露到 `:8080`。
- CR-006：不得修改三个现有 Vue 前端的路由、构建和运行行为。
- CR-007：React 日志查看器作为独立应用存在，不要求现有 Vue 组件或 KDesign/Element Plus 兼容。
- CR-008：第 13 节所列前端依赖、`package.json`、workspace 条目和锁文件变更已经用户确认，但实现阶段仍必须纳入对应 TASK 的明确文件范围；新增未列依赖需重新确认。

## 8. 可观测性与调试要求

- OD-001：查看器自身日志至少记录启动地址、日志根目录、订阅连接建立/关闭、文件打开/重置失败、队列溢出和优雅退出。
- OD-002：查看器自身日志不得复制业务日志正文，不得打印检测到的 token、完整请求体或本地敏感配置。
- OD-003：提供 `GET /healthz`，用于确认查看器 HTTP 进程可用；该接口不代表 12 个业务服务健康。
- OD-004：底部状态栏展示 SSE 状态、已接收条数、客户端缓冲区使用量、丢弃条数和已选服务数。
- OD-005：开发构建可输出解析失败、文件重置和 SSE 重连的诊断信息；生产式本地运行默认不输出逐行调试日志。

## 9. 错误处理与降级要求

- EF-001：日志目录不存在时，后端继续运行并等待目录/文件出现，UI 显示无服务日志状态。
- EF-002：单个日志文件不可读时，该服务返回可见错误状态，其他服务继续工作。
- EF-003：PID 文件异常时，该服务状态降级为 unknown/offline，并记录不含敏感内容的诊断日志。
- EF-004：无法解析时间、级别、调用位置或 JSON 尾部字段时，保留原消息并将缺失字段留空。
- EF-005：SSE 断线时客户端保留现有缓冲区、指数或浏览器策略重连，并显示状态；不得清空页面。
- EF-006：事件缺口无法恢复时，通过显式 reset/snapshot 流程恢复，并向用户说明可能存在缺口。
- EF-007：复制 API 不可用或被浏览器拒绝时显示失败提示，不得无反馈失败。
- EF-008：静态资源缺失或嵌入失败必须在构建阶段失败，不允许启动后返回不完整空页面。

## 10. 安全与安全性要求

- SS-001：HTTP 服务必须默认且强制绑定 `127.0.0.1`；第一版不提供远程监听配置。
- SS-002：不实现登录鉴权的前提是 SS-001 得到满足；若未来允许非 loopback 监听，必须先新增独立安全设计并经确认。
- SS-003：后端只允许访问固定白名单对应的 `.dev/logs` 和 `.dev/pids` 文件，不接受任意路径。
- SS-004：所有文件路径必须从仓库根目录解析并验证位于允许目录内，拒绝符号链接或路径穿越导致的越界访问。
- SS-005：React 以文本节点渲染日志；禁止使用未经清理的 `dangerouslySetInnerHTML`。
- SS-006：静态响应设置合理的 CSP、`X-Content-Type-Options: nosniff` 和 `Referrer-Policy`；SSE 与 API 禁止缓存。
- SS-007：页面应提示本地日志可能包含个人数据或凭据，用户不得将查看器暴露到局域网或公网。
- SS-008：查看器 API 必须是只读的；“清空”只清理客户端内存。
- SS-009：日志内容、搜索条件和剪贴板操作不得发送给第三方服务。

## 11. 验收标准

- AC-001：给定 12 个服务目录，服务 API 返回准确名称、分组、端口、运行状态、日志存在性和最后更新时间。
- AC-002：给定已有日志文件，首次连接最多加载配置上限内的末尾日志，并在后续追加完整行时实时展示。
- AC-003：日志文件截断、删除重建或替换后，查看器不退出，发送 reset 分隔事件并继续读取新内容。
- AC-004：包含 ANSI、Zap console、JSON 尾部、Gin、多行 Go 堆栈和 Vite 文本的样例均能安全展示；解析失败的内容不丢失。
- AC-005：两个 SSE 客户端并发订阅时互不阻塞；慢客户端导致自身队列丢弃时，其他客户端仍收到日志。
- AC-006：SSE 断开重连可用 `Last-Event-ID` 补发可恢复事件；不可恢复时执行显式 reset/snapshot。
- AC-007：服务、级别和普通文本筛选可组合；无结果状态保留条件并可一键清除。
- AC-008：用户滚动离开底部或点击暂停后仍接收数据，并可通过恢复/跳转到最新查看缓冲日志。
- AC-009：浏览器缓冲超过 10,000 条时淘汰最旧记录并展示丢弃计数，页面保持可操作。
- AC-010：选中日志后详情面板不覆盖日志列，能复制完整日志和可识别关联 ID。
- AC-011：无日志目录、单文件不可读、PID 陈旧和 SSE 断线均有对应可见状态，且不影响无关服务。
- AC-012：HTTP 服务只监听 `127.0.0.1:8090`，任意文件路径请求不可达，日志内容不作为 HTML 执行。
- AC-013：前端通过 typecheck、单元测试和生产构建；Go 后端通过 `go test ./...`、`go vet ./...` 和 `gofmt` 检查。
- AC-014：1440×900 和 1366×768 人工验收与 `design/screens/` 对应基线一致，且无页面级双滚动条、日志正文遮挡或关键操作溢出。
- AC-015：现有 12 个服务、Gateway 和三个 Vue 前端的现有构建/测试不因本功能发生行为变化。
- AC-016：当前筛选结果可导出为 UTF-8 纯文本 `.log`，导出内容不超过客户端缓冲范围，且不会触发新的服务端日志读取。
- AC-017：刷新页面后仅恢复合法的侧栏折叠状态和详情面板宽度；日志、搜索词、服务选择和级别筛选均不恢复。
- AC-018：生产构建不请求 CDN、Google Fonts 或其他第三方资源，页面可见位置包含敏感日志和禁止外部暴露提示。

## 13. 已确认技术决策

- D-001：实现目录采用仓库根目录下的 `dev-log-viewer/`；同一目录作为独立 Go module 根和前端 package 根，并通过 `go:embed` 嵌入 `web/dist`。
- D-002：将 `dev-log-viewer` 加入根 `pnpm-workspace.yaml`，允许新增 React、TypeScript、Vite、Tailwind CSS、Vitest、Testing Library 和 `@tanstack/react-virtual` 依赖，并在专门 TASK 中更新 `pnpm-lock.yaml`。
- D-003：默认地址为 `127.0.0.1:8090`，Vite 开发服务器使用 `127.0.0.1:8091` 并代理 `/api` 和 `/healthz`。
- D-004：首屏快照默认 300 行/服务、最大 1000 行/服务，浏览器缓冲上限 10,000 条；容量不在 UI 中开放调整，但后端容量保留受校验的环境变量配置。
- D-005：第一版服务运行状态只使用 PID 文件 + 进程存活检查，不主动探测 gRPC/HTTP 端口健康。
- D-006：`start-dev.sh`/`stop-dev.sh` 新增显式 `logs|log-viewer` target，但不加入无参数或 `all` 默认集合。
- D-007：第一版提供客户端纯文本 `.log` 导出，不提供服务端导出或 JSONL。
- D-008：第一版不实现自动脱敏规则；页面必须提示日志可能包含敏感信息，查看器保持 loopback-only。
- D-009：只通过 localStorage 持久化侧栏折叠状态和详情面板宽度，不持久化日志、查询或筛选条件。
- D-010：不允许联网加载字体或其他 UI 资源，使用系统可用字体及回退字体。
- D-011：日志列表使用 `@tanstack/react-virtual`；模块必须提供 README，说明启动、端口、配置、安全边界和故障排查。
- D-012：文件 tail 第一版采用约 250ms 的 Go 标准库轮询；若无法达到 NFR-001，再通过方案变更评估 `fsnotify`。
