# Internationalized Runtime Messages

Smart Recruit uses one deployment-level locale for backend logs, API/SSE system
messages, and the three authenticated product frontends.

## Configuration

Set `APP_LOCALE` to one of:

- `zh-CN` (default)
- `en-US`

All processes in one deployment must receive the same value. The local launcher,
Docker Compose, microservice Compose, and Kubernetes ConfigMaps default to
`zh-CN`. Do not override individual services. Changing the locale requires an
atomic backend restart and a browser refresh; frontend images do not need to be
rebuilt because applications read `GET /api/v1/public/runtime-config` before
mounting.

Example:

```bash
APP_LOCALE=en-US ./start-dev.sh
```

An unsupported value fails backend startup rather than silently selecting a
different language.

## Message contract

Canonical catalogs live in
`smart-recruit-platform-go/i18n/catalogs/{zh-CN,en-US}.json`. Keys are stable
internal contracts grouped by domain, for example `common.success`,
`validation.invalid_body`, `billing.order_pending`, and
`log.gateway.started`.

HTTP responses retain `code`, `msg`, `data`, and `request_id`, and add
`message_key`. `message_key` is stable; `msg` is localized at the Gateway.
Service-to-service protobuf `msg` values use keys. SSE system errors use the
same `message_key` plus localized `msg`. User input, model answers, and domain
content are never translated.

Application logs use an event key as the main message. The logging core renders
it in the configured locale and adds `event_key` and `locale`. Raw database,
network, and vendor errors may be retained only in a structured `cause` field;
they must not be returned to users or used as the main log message.

Unknown keys never fall back to the other language. Production emits the safe
generic message in the configured locale. Catalog validation and CI fail on
missing keys, mismatched placeholders, stale generated frontend catalogs, and
unmanaged messages at governed response boundaries.

## Frontend catalog generation

The TypeScript catalog is generated from the canonical backend catalogs:

```bash
node scripts/generate-i18n.mjs
node scripts/generate-i18n.mjs --check
node scripts/check-i18n-governance.mjs
```

Commit the generated `packages/shared/src/i18n/generated.ts` whenever the
canonical catalogs change.

## Troubleshooting

1. Check every container or process has the same `APP_LOCALE`.
2. Call `/api/v1/public/runtime-config` and confirm its `data.locale`.
3. Check startup logs for the structured `locale` field.
4. Regenerate the frontend catalog if the CI stale-catalog check fails.
5. Treat a generic localized message as evidence of an unmigrated or unknown
   key; inspect the server-side structured `cause` and add a canonical key when
   the condition needs a specific user-facing message.
